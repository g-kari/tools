# リリースノート更新ルール

ユーザーに影響のある変更を加えたら、必ず `app/routes/release-notes.tsx` の `releases` 配列を更新すること。

## 更新が必須となる変更

以下のタイプの変更は **必ず** リリースノートに記載する：

| タイプ     | 対象となる変更                                                   |
| ---------- | ---------------------------------------------------------------- |
| `feat`     | 新規ツール追加・既存ツールへの新機能追加                         |
| `fix`      | ユーザーが気付く不具合の修正・UI バグ修正                        |
| `security` | 脆弱性対応・セキュリティパッチ                                   |
| `refactor` | ユーザー体験に影響するリファクタ（動作変更・パフォーマンス改善） |

## 記載不要な変更（任意）

以下はリリースノートに載せなくてよい：

- `test` 単体のテスト追加・カバレッジ向上
- `chore` CI 設定・lint 設定・依存関係の内部更新
- `docs` コード内コメント・ドキュメントのみの更新
- 内部リファクタ（API・挙動に変化なし）

ただし複数束ねて目立つ変更になるなら記載してよい。

## 記載手順

1. `app/routes/release-notes.tsx` を開く
2. `releases` 配列の **先頭のリリース** を確認：
   - **今日の日付と同じ version / date** なら、その `entries` に追加する
   - 日付が違うなら、新しい `Release` オブジェクトを配列の先頭に追加する
3. `ReleaseEntry` は最小限 `{ type, title }`。必要なら `description` を添える
4. `title` は一行で完結させる。詳細は `description` に書く
5. 日付は YYYY-MM-DD 形式の当日
6. version は原則 `YYYY.MM`（同日の複数リリースは `YYYY.MM.N` などで衝突回避）

## 記載例

```ts
{
  version: "2026.04",
  date: "2026-04-17",
  headline: "〜まとめ見出し（任意）",
  entries: [
    {
      type: "feat",
      title: "新ツール追加: ○○",
      description: "任意の詳細説明",
    },
    { type: "fix", title: "○○ の表示崩れを修正" },
  ],
},
```

## チェック

リリースノートを更新したら、ユニットテストが通ることを確認：

```bash
vp test run tests/unit/release-notes.test.ts
```

`releases` データの整合性（日付降順・既知タイプ）がテストされているため、構造を崩すと落ちる。
